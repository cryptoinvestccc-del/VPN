# Обфускатор WireGuard-трафика

Прозрачный UDP-прокси, который прячет форму WireGuard-трафика от DPI, не
трогая криптографию самого WireGuard. Подробный дизайн и модель угрозы —
в [`docs/DESIGN.md`](docs/DESIGN.md).

Суть: WireGuard шифрует данные как обычно (Curve25519, ChaCha20-Poly1305,
forward secrecy — всё как в оригинале). Этот проект оборачивает уже
зашифрованные WG-пакеты в ещё один слой: AEAD-шифрование PSK-ключом со
случайным паддингом и мусорными пакетами, чтобы DPI не мог опознать
трафик по сигнатуре/длинам/поведению.

## Компоненты

- `internal/obfuscator` — ядро: `Wrap`/`Unwrap` пакета (nonce +
  XChaCha20-Poly1305 + паддинг с учётом MTU), генерация junk-пакетов.
- `internal/transport` — два прокси: `RunClient` (локально принимает
  WG-пакеты, шлёт наружу обфусцированными) и `RunServer` (принимает
  обфусцированные, форвардит на локальный WG-сервер).
- `internal/transport/tls_auth.go` — вывод ключей сессии из PSK и
  TLS-exporter, авторизация пира, поведение веб-сервера для
  неавторизованных соединений.
- `cmd/obfsclient`, `cmd/obfsserver` — CLI-обёртки с конфигом из YAML;
  `cmd/gencert` — генерация сертификата и PSK; `cmd/obfsctl` — выдача и
  отзыв учётных данных клиентов.
- `internal/clients` — список учётных данных, атомарная перезагрузка,
  проверка на дубли идентификаторов и битые ключи.

## Быстрый старт (тестовый стенд)

```bash
go build ./...
go test -race ./...      # модульные и нагрузочные тесты
./scripts/e2e_test.sh    # сквозной прогон собранных бинарников
```

`scripts/e2e_test.sh` поднимает реальные процессы с реальными конфигами и
проверяет то, что модульные тесты не покрывают: оба режима, размеры
пакетов вплоть до jumbo, молчание UDP-порта в ответ на пробинг, реальное
TLS-рукопожатие, ответ веб-сервера на неавторизованную пробу, отказ
клиенту с неверным PSK, переподключение после перезапуска сервера, отказ
при несовпадении pin и чистое завершение по SIGTERM.

Интеграция с **настоящим** WireGuard (отдельный модуль, чтобы gVisor не
попадал в зависимости продакшен-бинарников):

```bash
cd test/wireguard && go test -short ./...
```

Поднимает два реальных WireGuard-пира через wireguard-go с userspace-
стеком netstack — без ядерного модуля и без root — и гоняет TCP сквозь
наш туннель в обоих режимах. Без `-short` дополнительно проверяется
переустановка сессии WireGuard (rekey) на ходу, это занимает ~2.5 минуты.

Фаззинг разборщиков, доступных атакующему до аутентификации:

```bash
go test -run='^$' -fuzz=FuzzUnwrap -fuzztime=60s ./internal/obfuscator/
go test -run='^$' -fuzz=FuzzReadFrame -fuzztime=60s ./internal/transport/
```

Всё перечисленное выполняется в CI на каждый push
([`.github/workflows/ci.yml`](.github/workflows/ci.yml)): сборка, vet,
gofmt, тесты под race-детектором, интеграция с настоящим WireGuard,
сквозной прогон и фаззинг. Отдельной задачей — длинный тест на
переустановку сессии WireGuard.

Результаты аудита продукта, список исправленных дефектов и честный
перечень того, чего в продукте нет — в [`docs/AUDIT.md`](docs/AUDIT.md).

## Разворачивание (быстрый способ)

```bash
sudo ./deploy/install.sh server   # на VPS
sudo ./deploy/install.sh client   # на клиентской машине
```

Скрипт собирает бинарник, создаёт непривилегированного пользователя
`obfsvpn`, кладёт шаблон конфига в `/etc/obfsvpn/` (0640, root:obfsvpn —
там будет лежать PSK) и systemd-юнит. Дальше — вручную отредактировать
конфиг (вписать PSK и адреса) и `systemctl enable --now obfsserver`
(или `obfsclient`). Юниты уже настроены с `ProtectSystem=strict`,
`NoNewPrivileges=true` и работой не под root.

## Разворачивание (вручную)

### 1. На сервере (VPS)

Настрой обычный WireGuard-сервер, но привяжи его **только к localhost**
(не к публичному интерфейсу) — публично торчать должен только
`obfsserver`:

```ini
# /etc/wireguard/wg0.conf
[Interface]
ListenPort = 51821
Address = 10.0.0.1/24
PrivateKey = ...
MTU = 1376
# без публичного форвардинга порта — только 127.0.0.1
```

**`MTU = 1376` обязателен, и это не косметика.** Значение WireGuard по
умолчанию (1420) рассчитано на то, что он идёт прямо поверх IP. Здесь он
идёт внутри ещё одной инкапсуляции, которая добавляет 42 байта. Измерение
на живом WireGuard (`test/wireguard`) показало пакеты до 1424 байт: с
обёрткой это 1466, и на IPv6-маршруте (1466 + 8 UDP + 40 IPv6 = 1514)
такой пакет **фрагментируется**. Фрагментация бьёт по скорости и сама по
себе является заметным паттерном — то есть работает против обфускации.

Арифметика значения 1376: 1500 − 40 (IPv6) − 8 (UDP) = 1452 бюджет на
обёрнутый пакет; −42 (наша обёртка) = 1410; −32 (заголовок и тег
WireGuard) = 1378; округление вниз до кратного 16 (паддинг WireGuard) =
1376. Если пакеты всё же превышают бюджет, `obfsserver`/`obfsclient`
однократно пишут об этом в лог с этой же рекомендацией.

Скопируй `examples/obfsserver.yaml` → `obfsserver.yaml`, впиши свой PSK
(`openssl rand -base64 32`) и запусти:

```bash
go run ./cmd/obfsserver -config obfsserver.yaml
```

Открой публично только порт `listen_wire_addr` (по умолчанию 51820/udp) в
файрволе — порт реального WG (51821) должен остаться закрытым снаружи.

### 2. На клиенте

Настрой WireGuard-клиента с `Endpoint = 127.0.0.1:51821` (локальный порт,
на который слушает `obfsclient`). Скопируй `examples/obfsclient.yaml`,
впиши тот же PSK и IP сервера, запусти:

```bash
go run ./cmd/obfsclient -config obfsclient.yaml
```

Подними WG-интерфейс (`wg-quick up wg0`) — трафик пойдёт через
`obfsclient` → обфускация → `obfsserver` → реальный WG.

### Режим TLS (устойчивее к активному DPI-пробингу)

По умолчанию (`mode: udp`) канал — просто обфусцированный UDP: DPI видит
UDP-трафик на нестандартном порту, что само по себе подозрительно в
странах со строгой фильтрацией. Режим `mode: tls` заворачивает трафик в
настоящее TLS 1.3-соединение — порт сервера отвечает как обычный HTTPS,
включая полноценное рукопожатие, что проходит и активный пробинг DPI.

На сервере:

```bash
go run ./cmd/gencert -cn www.example.com -cert server.crt -key server.key
```

Команда печатает готовые строки конфига: `psk` и `pinned_cert_sha256`.
Используй `examples/obfsserver-tls.yaml` и `examples/obfsclient-tls.yaml`
как шаблоны. Сертификат самоподписанный: доверие устанавливается не через
публичный CA, а через pinning отпечатка (как в Trojan/ShadowTLS) — клиент
откажется соединяться, если отпечаток не совпадёт (защита от MITM).

**Два значения из вывода `gencert` играют разные роли, и путать их
нельзя:**

- `psk` — **секрет**, идёт в оба конфига. Это пропуск клиента: ключи
  пакетов выводятся из него вместе с TLS-сессией. Без него любой, кто
  завершил рукопожатие с сервером, смог бы слать трафик в WireGuard —
  сертификат предъявляется каждому подключающемуся, поэтому его отпечаток
  секретом не является и роль пропуска играть не может.
- `pinned_cert_sha256` — **не секрет**, идёт только в конфиг клиента. Он
  аутентифицирует сервер перед клиентом (защита от MITM).

**Соединения, не прошедшие аутентификацию** (пробы DPI, сканеры,
случайные браузеры), передаются fallback-обработчику. Если задан
`fallback_addr` с реальным веб-сервером — порт отвечает ровно как сайт за
ним и от обычного HTTPS-хостинга неотличим. Без него возвращается
правдоподобный ответ в стиле nginx. Это принципиально: сервер, который
принимает байты, не отвечает и не разрывает соединение, опознаётся по
тому, *как он отказывает*.

## Учётные данные на каждого клиента

Общий `psk` удобен для нескольких своих устройств, но отозвать доступ
одному из них можно только сменив ключ всем — каждый отзыв становится
простоем для всех. Поэтому сервер умеет работать со списком клиентов, где
у каждого свой ключ.

```bash
obfsctl -file /etc/obfsvpn/clients.yaml add laptop      # выдать доступ
obfsctl -file /etc/obfsvpn/clients.yaml revoke laptop   # отозвать
obfsctl -file /etc/obfsvpn/clients.yaml list            # кто имеет доступ
systemctl reload obfsserver                             # применить
```

`add` печатает ключ, который вписывается **только** в конфиг этого
клиента. На сервере вместо `psk` указывается `clients_file`:

```yaml
clients_file: "/etc/obfsvpn/clients.yaml"
```

Шаблон — `examples/clients.yaml`.

Как это устроено и что из этого следует:

- **Отзыв не задевает остальных.** Проверяется тестом: после отзыва
  одного клиента второй продолжает работать без разрыва.
- **Отзыв доходит до живых сессий**, а не только до новых подключений —
  иначе отозванное устройство сохраняло бы доступ, пока само не
  переподключится. Занимает до ~30 секунд.
- **Перезагрузка по SIGHUP** не разрывает чужие туннели. Если в файле
  ошибка, прежний набор остаётся в силе: опечатка не должна отрезать
  всех.
- **На проводе идентификатор клиента не появляется.** Сервер определяет
  отправителя перебором ключей — но только при установлении сессии;
  дальше пакет расшифровывается одним ключом, как и раньше. Так же
  устроен сам WireGuard: поиск по списку пиров при рукопожатии, потом
  индекс сессии.
- **Ротация ключа отдельного клиента** работает так же, как для общего:
  `psk_previous` рядом с новым `psk`.

## Ротация общего PSK без даунтайма

1. Сгенерировать новый ключ: `openssl rand -base64 32`.
2. На сервере: старый `psk` переносим в `psk_previous`, новый пишем в
   `psk`. Перезапустить `obfsserver` — он теперь принимает пакеты под
   обоими ключами.
3. На каждом клиенте по очереди: обновить `psk` на новый, перезапустить
   `obfsclient`. Клиенты, которые ещё не обновлены, продолжают работать
   через `psk_previous` на сервере.
4. Когда все клиенты переведены — убрать `psk_previous` из конфига
   сервера и перезапустить его (закрывает fallback-путь).
