# Обфусцирующий транспорт для WireGuard

## Цель

Скрыть WireGuard-трафик от DPI-систем (по сигнатуре пакетов, длинам,
поведенческим паттернам), не трогая криптографию самого WireGuard.
WireGuard остаётся эталонной, проверенной реализацией (Noise protocol
framework, Curve25519, ChaCha20-Poly1305) — мы не изобретаем шифрование,
мы прячем форму трафика.

## Модель угрозы

- Пассивный DPI на маршруте между клиентом и сервером, который:
  - ищет известные magic-байты / фиксированные длины WireGuard-пакетов;
  - анализирует статистику размеров и таймингов (entropy/behavioral analysis);
  - может делать active probing (посылать свои пакеты на подозрительный порт
    и смотреть на ответ).
- НЕ защищаемся от: компрометации самого VPN-сервера, endpoint-атак на
  устройство клиента, глобального пассивного наблюдателя с полным трафиком
  за длительный период (traffic correlation).

## Архитектура

```
[WG-клиент] --UDP(127.0.0.1)--> [obfsclient] --UDP(обфусцировано)--> [obfsserver] --UDP(127.0.0.1)--> [WG-сервер]
```

`obfsclient` и `obfsserver` — прозрачные UDP-прокси. WireGuard ничего не
знает об обфускации: смотрит на localhost, как будто говорит напрямую с
пиром.

## Слои обфускации (v1)

1. **Внешнее шифрование пакета.** Каждый UDP-датаграм оборачивается:
   `nonce (24 байта) || XChaCha20-Poly1305(payload || padding)`.
   Ключ — PSK, задаваемый при настройке (out-of-band, как WG-ключи);
   в TLS-режиме из PSK выводится ключ сессии, см. п.5.
   Это делает содержимое пакета неотличимым от случайного шума —
   никаких магических байт WireGuard снаружи не видно.

2. **Паддинг переменной длины.** Перед шифрованием к payload добавляется
   случайный паддинг (0..255 байт, длина кодируется в первых двух байтах
   plaintext перед шифрованием). Ломает фиксированные длины
   handshake-init/response/keepalive, по которым легко детектится WG.

   Паддинг обрезается так, чтобы итоговый пакет оставался в пределах
   `SafeWireSize`: доведение полноразмерного пакета за MTU вызвало бы
   фрагментацию, а это и потеря скорости, и характерный паттерн — то есть
   ровно то, против чего паддинг и вводился. Сами байты паддинга — нули:
   они внутри AEAD-шифрования и наружу выходят шифротекстом при любом
   содержимом (так же поступает TLS 1.3, RFC 8446 §5.4).

3. **Junk-пакеты.** Перед первым handshake клиент отправляет N (случайное,
   настраиваемое) мусорных UDP-пакетов случайной длины со случайным
   содержимым. Сервер их отбрасывает (не проходят AEAD-проверку —
   безопасно игнорируются). Это тот же приём, что в AmneziaWG
   (параметры Jc/Jmin/Jmax), ломает поведенческую эвристику "первый пакет
   выглядит как WG handshake".

4. **TLS-транспорт (реализовано).** Вместо имитации заголовков — настоящее
   TLS 1.3 рукопожатие (`internal/transport/tls_transport.go`). Сервер
   поднимает `tls.Listen` с самоподписанным сертификатом; клиент
   подключается через `tls.Dial` и проверяет сервер не через публичный
   CA (сертификат самоподписанный), а через pinning SHA-256 отпечатка
   сертификата (`tlscert.PinFromConnState`), зашитый заранее в конфиг.
   Внутри TLS-канала обфусцированные пакеты передаются в виде
   length-prefixed фреймов (`writeFrame`/`readFrame`), поскольку TLS —
   потоковый, а не датаграммный транспорт.

   Почему это сильнее фейковых заголовков: активный DPI-пробинг (GFW-style,
   ТСПУ) не просто смотрит на байты, а сам пытается говорить с портом —
   слать TLS ClientHello и смотреть, ответит ли сервер настоящим
   TLS ServerHello/сертификатом. С фейковыми заголовками такая проверка
   сразу палит подделку. С реальным `tls.Listen` сервер проходит
   рукопожатие по-настоящему.

5. **Авторизация и поведение при отказе.** Рукопожатия недостаточно:
   сертификат видит каждый подключающийся, поэтому его отпечаток не
   секрет, и любой посторонний вычисляет то же значение TLS exporter, что
   и сервер. Ключи пакетов поэтому выводятся из **двух** входов:

   ```
   traffic_key = HKDF-SHA256(secret = TLS-exporter, salt = PSK,
                             info = "obfsvpn traffic key v2")
   ```

   PSK даёт авторизацию (подделать нельзя), exporter — привязку к
   сессии (кадры одного соединения нельзя переиграть в другое). Отдельного
   обмена аутентификацией нет: первый же кадр либо расшифровывается, либо
   нет, поэтому на проводе авторизация ничем не отличается от обычного
   трафика.

   Соединения, не прошедшие проверку, уходят в fallback: при заданном
   `fallback_addr` — проксируются на настоящий веб-сервер, иначе получают
   ответ в стиле nginx. Это столь же важно, как и сама авторизация: сервер,
   который принимает произвольные байты, ничего не отвечает и не
   разрывает соединение, опознаётся по тому, *как он отказывает* — так не
   ведёт себя ни один настоящий HTTPS-сервер. Тем же приёмом пользуются
   Trojan и ShadowTLS.

## Почему это безопасно (а не "своя крипто")

- Единственный новый крипто-примитив здесь — использование ChaCha20-Poly1305
  (стандартная, проверенная AEAD-схема, та же, что в TLS 1.3 и самом
  WireGuard) в новом контексте (обёртка пакета). Мы не проектируем новую
  математику, не пишем свой шифр.
- PSK-схема без forward secrecy на этом слое — это осознанный компромисс:
  компрометация PSK раскрывает только факт "это обфусцированный WG-трафик",
  но не внутренний WireGuard-трафик (у него свой Noise-handshake с
  forward secrecy). Обфускация — это слой маскировки, не слой
  конфиденциальности; конфиденциальность обеспечивает WireGuard.

## Формат пакета (провод)

```
+----------------+-------------------------------------------+
| nonce (24B)    | XChaCha20-Poly1305(plaintext) + tag (16B) |
+----------------+-------------------------------------------+

plaintext = pad_len (2B) || real_wg_payload || zero_padding(pad_len)
```

Nonce — 24 байта (XChaCha20-Poly1305, а не 12-байтовый вариант): nonce
генерируется случайно для каждого пакета, а при 96-битном nonce на
нагруженном сервере со статическим PSK счёт пакетов подходит к границе
дня рождения за часы работы. 192-битный nonce делает повторение
статистически недостижимым при любом сроке жизни ключа.

Junk-пакеты — это просто случайные байты случайной длины (64..1400,
диапазон правдоподобных размеров реального трафика), без валидной
AEAD-структуры; сервер пытается их расшифровать, получает ошибку тега —
молча дропает.

## Roadmap

- [x] v1: XOR/AEAD обёртка + паддинг + junk-пакеты (этот репозиторий, старт)
- [x] v1: конфигурация (PSK, эндпоинты, параметры паддинга/junk) через YAML
- [x] v2: настоящий TLS-транспорт с pinning сертификата (устойчив к
      активному DPI-пробингу)
- [x] v1/v2: systemd-юниты, скрипт разворачивания (`deploy/install.sh`)
- [x] v2: ротация PSK без даунтайма (`Obfuscator.NewMulti` пробует
      несколько ключей на приём; см. README "Ротация PSK")
- [x] v3: привязка ключей к TLS-сессии. Ключи пакетов выводятся через
      `HKDF(secret = TLS-exporter, salt = PSK)` (`deriveTrafficObfuscator`
      в `internal/transport/tls_auth.go`): PSK авторизует пира, exporter
      привязывает ключи к конкретному соединению, поэтому кадры из одной
      сессии нельзя переиграть в другую, и на каждое переподключение
      ключи меняются сами.

      Промежуточная версия этого пункта выводила ключ **только** из
      exporter и объявляла PSK необязательным. Это было ошибкой и
      исправлено: сертификат предъявляется каждому подключающемуся,
      поэтому любой посторонний вычислял тот же exporter и мог слать
      трафик в WireGuard. Разбор — в `docs/AUDIT.md`, п.12.

- [x] v3: поведение веб-сервера для неавторизованных соединений
      (`fallback_addr` или канонный ответ nginx) — закрывает опознание
      порта по характеру отказа.

- [ ] v4: индивидуальные учётные данные на клиента (сейчас PSK общий,
      поэтому отзыв доступа одному требует ротации для всех).

- [ ] v4: маскировка таймингов (сейчас маскируются только размеры;
      ритм перехэндшейков WireGuard каждые 2 минуты виден снаружи).
