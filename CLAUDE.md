# Правила для кода в этом репозитории

## Обязательные проверки безопасности

Любое изменение кода проходит эти три проверки до коммита и до выпуска.
Если проверка не пройдена — изменение не готово, как бы хорошо оно ни работало.

### 1. Никаких секретов на стороне клиента и в репозитории

- Серверные ключи, токены и пароли (API-ключи вида `sk-…`, `service_role`,
  токены ботов, ключи сервисных аккаунтов, ключи подписи, пароли от баз)
  никогда не попадают в код приложения, веб-страницы, APK/AAB, логи и git.
- Клиент получает только то, что безопасно показать любому: публичные
  ключи и адреса. Всё секретное живёт на сервере — в переменных окружения,
  файлах с правами `600` или хранилище секретов.
- Перед коммитом и перед выпуском — поиск по изменениям, истории git и
  собранному артефакту (APK, bundle сайта): `sk-`, `service_role`,
  `PRIVATE KEY`, `private_key_id`, токены вида `123456:AA…`, `AKIA…`.
- Ошибки и логи не должны цитировать секрет (например, URL с токеном).

### 2. Каждое хранилище данных закрыто по умолчанию

- В любой базе с доступом от клиента (Supabase и т. п.) включён RLS на
  **каждой** таблице, и у каждой таблицы есть явные политики. Таблица без
  политик или с `using (true)` для записи — ошибка.
- Доступ по умолчанию — запрещён; открывается ровно то, что нужно.
- Серверные эндпоинты и боты отвечают только тем, кому положено
  (проверка прав/allowlist на сервере, а не в интерфейсе).

### 3. Проверка владельца на каждом запросе по идентификатору

- Любой запрос, где клиент передаёт id (записи, пользователя, ключа,
  файла), проверяет на сервере, что объект принадлежит именно этому
  пользователю. Id от клиента — не доказательство прав.
- Удаление и изменение требуют секрета или сессии владельца, а не только
  знания идентификатора.
- На каждый такой эндпоинт — тест: запрос с чужим id должен быть отклонён.

## Как отчитываться

В описании изменения указывать, как проверены все три пункта (какой
поиск, какие тесты). Если пункт неприменим — написать почему.
